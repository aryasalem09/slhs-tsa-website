## 2024-07-27 - LRU Cache Eviction Bypass in Rate Limiter
**Vulnerability:** The in-memory rate limiter in `src/lib/studio/rate-limit.ts` used a JavaScript `Map` to store login attempts, enforcing eviction when reaching `MAX_TRACKED_KEYS` (4096) by dropping the oldest inserted entry. Because existing active keys were updated in place without re-insertion, a spamming IP's rate limit entry remained the "oldest" and could be evicted prematurely if 4096 other keys were requested, thus bypassing the rate limiter.
**Learning:** In JavaScript, `Map` insertion order is not automatically updated when values are modified. Modifying an existing rate-limit record doesn't make it the "newest" entry without explicitly deleting and re-setting it.
**Prevention:** Implement explicit Least Recently Used (LRU) behavior in custom Map-based tracking code. When an entry is accessed or updated, use `Map.prototype.delete(key)` and `Map.prototype.set(key, value)` to push it to the end of the insertion order, protecting active tracking limits from being pushed out by garbage/flooding.
## 2026-08-02 - Rate Limiter IP Spoofing Fix
**Vulnerability:** The application was extracting the client IP address from `X-Forwarded-For` and `X-Vercel-Forwarded-For` by using the first element `[0]` in the comma-separated list. This allows an attacker to bypass rate limiting by spoofing their IP, as they can inject a fake IP at the start of the list, whereas trusted proxies (like Vercel) append the real IP at the end.
**Learning:** When retrieving client IPs from `X-Forwarded-For` for rate limiting, using the first element is insecure if the application is behind a proxy that appends to the list.
**Prevention:** Use `.at(-1)` or `.pop()` to extract the rightmost IP address from the `X-Forwarded-For` header, which represents the real IP appended by the trusted proxy.
